# Using ORMs correctly

ORMs speed up writing code but hide the real SQL. The three most common mistakes: N+1 queries, misused transactions, and auto-generated migrations run without anyone reading them. The examples below ran on PostgreSQL 16 with Prisma 7.10, Drizzle 0.45, TypeORM 1.1, Sequelize 6.37, SQLAlchemy 2.1, Django 6.1, GORM 1.31, ActiveRecord 8.1, including two concurrent transactions decrementing stock. On other versions, **re-check against the installed version** (official docs or the type files in `node_modules`) before use.

Eloquent (Laravel), JPA/Hibernate (Spring Boot) and EF Core (.NET) are covered with their frameworks: `references/laravel.md`, `references/spring.md`, `references/dotnet.md`.

## 1. General rules

- **Turn on SQL logging in dev** and watch the query count per request. A 20-row list that runs 21 queries is N+1.
- **Select only the columns you need** (`select`) for large lists and public APIs: faster, and you don't accidentally return sensitive fields.
- **Raw SQL is allowed** for complex queries (reports, CTEs, window functions), but always parameterized; never string concatenation.
- **Read auto-generated migrations**: an ORM can turn "rename column" into "drop column + add column" and lose data.
- **Never use automatic schema sync in production** (`synchronize`, `sync({ alter: true })`, `db push`, `AutoMigrate`): no history, and it can delete data.
- Transactions: every query inside must go through the transaction object (`tx`), not the root client; a query on the root client runs outside the transaction.
- **Decrement quantities (stock, credits, balances) with one conditional UPDATE and check the affected row count**: `UPDATE ... SET qty = qty - 1 WHERE ... AND qty >= 1`; 0 rows means not enough, so throw to roll back the whole transaction. Reading the quantity, checking it in code, then writing lets two concurrent requests both pass. Add `CHECK (qty >= 0)` in the DB as the last safety net. All examples below follow this; `OutOfStockError` is a project business error.

## 2. Prisma

```ts
// Avoid N+1: load relations in one call
const customers = await prisma.customer.findMany({
  where: { status: 'active' },
  select: { id: true, name: true, orders: { select: { id: true, total: true } } },
  take: 20,
});

// Interactive transaction: every query uses tx
const order = await prisma.$transaction(async (tx) => {
  const { count } = await tx.stock.updateMany({
    where: { productId, qty: { gte: 1 } },
    data: { qty: { decrement: 1 } },
  });
  if (count === 0) throw new OutOfStockError(productId);   // throw = rollback
  return tx.order.create({ data: { customerId, total } });
});

// Parameterized raw SQL (tagged template). Avoid $queryRawUnsafe with user input.
const rows = await prisma.$queryRaw`SELECT id FROM customers WHERE email = ${email}`;
```

- Prisma 7: the client is generated by `generator "prisma-client"` with an `output`, the connection URL lives in `prisma.config.ts`, and you construct it with a driver adapter (`new PrismaClient({ adapter: new PrismaPg({ connectionString }) })`).
- Install the `prisma` CLI at the **same major** as `@prisma/client` (e.g. `prisma@7`) and check `npx prisma --version`: the `latest` tag of the `prisma` package has been seen pointing at an RC of a new major that lacked the `generate` and `migrate` commands.
- Migrations: `prisma migrate dev --create-only` to generate SQL, read/edit it, then apply; production runs `prisma migrate deploy`. `prisma db push` is for prototypes only.
- `CREATE INDEX CONCURRENTLY` and other statements that can't run in a transaction: hand-write the SQL in the migration and read the Prisma docs on running that migration outside a transaction.

## 3. Drizzle

```ts
import { and, eq, gte, sql } from 'drizzle-orm';

// Relational query: load relations (requires declared relations)
const list = await db.query.customers.findMany({
  where: (c, { eq }) => eq(c.status, 'active'),
  with: { orders: true },
  limit: 20,
});

await db.transaction(async (tx) => {
  const updated = await tx.update(stock)
    .set({ qty: sql`${stock.qty} - 1` })
    .where(and(eq(stock.productId, productId), gte(stock.qty, 1)))
    .returning({ productId: stock.productId });            // returning: Postgres, SQLite
  if (updated.length === 0) throw new OutOfStockError(productId);
  await tx.insert(orders).values({ customerId, total });
});

const result = await db.execute(sql`SELECT id FROM customers WHERE email = ${email}`);
// node-postgres driver: rows are in result.rows; postgres-js driver: result is an array
```

- Drizzle 1.0 changed relational queries (e.g. `where: { status: 'active' }` instead of a callback, `defineRelations()` instead of `relations()`); 0.x code running on 1.0 can silently ignore the `where` condition. Check the version before copying examples.
- Migrations: `drizzle-kit generate` (writes SQL files; read them) then `drizzle-kit migrate`. `drizzle-kit push` is for prototypes only.

## 4. TypeORM

```ts
import { MoreThanOrEqual } from 'typeorm';

const customers = await customerRepo.find({
  where: { status: 'active' },
  relations: { orders: true },
  take: 20,
});

await dataSource.transaction(async (manager) => {
  const res = await manager.decrement(Stock, { productId, qty: MoreThanOrEqual(1) }, 'qty', 1);
  if (res.affected === 0) throw new OutOfStockError(productId);
  await manager.save(Order, { customerId, total });
});

await dataSource.query('SELECT id FROM customers WHERE email = $1', [email]);
```

- `synchronize: true` only locally; production uses `migration:generate` → read → `migration:run`.

## 5. Sequelize

```js
import { Op } from 'sequelize';

const customers = await Customer.findAll({ where: { status: 'active' }, include: [Order], limit: 20 });

await sequelize.transaction(async (t) => {
  const [affected] = await Stock.update(
    { qty: sequelize.literal('qty - 1') },
    { where: { productId, qty: { [Op.gte]: 1 } }, transaction: t },
  );
  if (affected === 0) throw new OutOfStockError(productId);
  await Order.create({ customerId, total }, { transaction: t });
});
```

- Pass `{ transaction: t }` to **every** call; forget it and that call runs outside the transaction. No `sync({ alter: true })` in production; use sequelize-cli migrations.

## 6. SQLAlchemy 2.x

```python
from sqlalchemy import select, text, update
from sqlalchemy.orm import selectinload

with Session(engine) as session:
    stmt = select(Customer).where(Customer.status == "active").options(selectinload(Customer.orders)).limit(20)
    customers = session.scalars(stmt).all()
    rows = session.execute(text("SELECT id FROM customers WHERE email = :email"), {"email": email}).all()

with Session(engine) as session, session.begin():
    result = session.execute(
        update(Stock).where(Stock.product_id == product_id, Stock.qty >= 1).values(qty=Stock.qty - 1)
    )
    if result.rowcount == 0:
        raise OutOfStockError(product_id)
    session.add(Order(customer_id=customer_id, total=total))
    # commits on leaving the block, rolls back on error
```

- With mypy type checking: `Session.execute` is typed as `Result`, so `.rowcount` is a type error even though it works; use `cast(CursorResult[Any], session.execute(...))`, or add `.returning(Stock.product_id)` and check `result.first() is None`.

- `selectinload` for one-to-many, `joinedload` for many-to-one. Set `lazy="raise"` on a relationship to make lazy loads fail immediately in dev.
- Migrations: Alembic `alembic revision --autogenerate -m "..."` → read the file → `alembic upgrade head`.

## 7. Django ORM

```python
from django.db import transaction
from django.db.models import F

customers = Customer.objects.filter(status="active").prefetch_related("orders")[:20]
orders = Order.objects.select_related("customer")[:20]   # many-to-one / one-to-one: JOIN

with transaction.atomic():
    updated = Stock.objects.filter(product_id=product_id, qty__gte=1).update(qty=F("qty") - 1)
    if updated == 0:
        raise OutOfStockError(product_id)   # raising inside atomic() = rollback
    Order.objects.create(customer_id=customer_id, total=total)
```

- `select_related` for FK/one-to-one (JOIN), `prefetch_related` for reverse FK/many-to-many (second query).
- Migrations: `makemigrations` → `sqlmigrate app 0005` to see the SQL → `migrate`.

## 8. GORM (Go)

```go
var customers []Customer
db.Preload("Orders").Where("status = ?", "active").Limit(20).Find(&customers)

err := db.Transaction(func(tx *gorm.DB) error {
    res := tx.Model(&Stock{}).Where("product_id = ? AND qty >= 1", pid).
        Update("qty", gorm.Expr("qty - 1"))
    if res.Error != nil {
        return res.Error // returning an error rolls back
    }
    if res.RowsAffected == 0 {
        return ErrOutOfStock
    }
    return tx.Create(&Order{CustomerID: cid, Total: total}).Error
})
```

- `AutoMigrate` never drops columns and doesn't replace controlled migrations; production uses a dedicated migration tool (golang-migrate, atlas, goose).

## 9. ActiveRecord (Rails)

```ruby
customers = Customer.where(status: "active").includes(:orders).limit(20)

ActiveRecord::Base.transaction do
  updated = Stock.where(product_id: product_id).where("qty >= 1").update_all("qty = qty - 1")
  raise OutOfStockError if updated.zero?   # raise = rollback, and the error propagates
  Order.create!(customer_id: customer_id, total: total)
end
```

- `strict_loading` turns lazy loads into errors in dev.
- Rails has no command that prints a migration's SQL without running it: run the migration on the dev DB and read the SQL in `log/development.log`, and set `config.active_record.schema_format = :sql` so the `db/structure.sql` diff shows the real DDL. `rails db:migrate:status` only shows which migrations have run.
- Don't use `raise ActiveRecord::Rollback` for business errors: the transaction rolls back but no error propagates, so the caller thinks it succeeded.

## 10. Connection pools and serverless

- Each app instance holds a pool; total connections = instances × pool size, which must stay below the DB's `max_connections`.
- Serverless (Vercel, Lambda, Cloudflare): each invocation may open a new connection. Use a pooler (PgBouncer, Neon/Supabase pooler, Prisma Accelerate) in transaction pooling mode.
- Transaction pooling keeps no session state between transactions: no session-level `SET`, session prepared statements or session advisory locks. In multi-tenant apps, set the tenant context inside each transaction (`references/multi-tenant.md`).
